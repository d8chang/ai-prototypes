How it's built

prototype-level detail

In production

Each skill is a folder Claude loads when a request matches its description: skills/<name>/SKILL.md plus any reference files. Each MCP server authenticates with OAuth as the signed-in user (Salesforce, Slack, monday.com, Lucidchart) or with a scoped service account (Snowflake, limited to marketing views). Every server is read-only by default. Skills can write in only two places, a Slack message or a monday.com item, and each write waits for a button press. Agents can also create new Lucidchart diagrams; they never edit existing ones.

In this prototype

Nothing leaves the page. The eight SKILL.md files are stored in the page, open from the skill cards, and download together as marketing.plugin. The mock layer exposes the same tool names a real server would, and each tool returns rows from one sample DATA object. Skills only reach data through those tools, so the run trace, the KPI row, and every result agree, and swapping the mock for a real MCP client would not change the skill code.

A mock MCP tool (simplified from this page's source)

// Same tool name and arguments as the real Salesforce MCP server,
// but it reads the page's sample DATA object instead of calling an API.
const TOOLS = {
  'salesforce.query_leads': ({ noActivityHours, campaign }) => {
    let rows = DATA.slaLeads;                     // new leads, last 14 days
    if (noActivityHours) rows = rows.filter(l => l.hrs > noActivityHours);
    if (campaign)        rows = rows.filter(l => l.camp === campaign);
    return rows;
  },
};

// Every skill reaches data through call(), which also writes the run trace.
function call(tool, args = {}) {
  const out = TOOLS[tool](args);
  trace.push([tool, formatArgs(args), out.length + ' rows']);
  return out;
}

// A skill is then just tool calls plus rendering:
const late = call('salesforce.query_leads', { noActivityHours: 48 });
// In production, call() becomes a real MCP request scoped by OAuth.
